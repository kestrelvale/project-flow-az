 # 项目交付物与交付契约管控 SOP (Project Delivery & Contract SOP)
 
 > **核心定位**：彻底根除“只管任务流转、不管最终交付”、“任务完成了却找不到实体产物”、“交付物无验证凭证、无统一大盘”的系统性顽疾。  
 > **版本标识**：`project-flow V4.2.0 (Delivery-First 交付决胜版)`  
 > **生效日期**：2026-09-15
 
 ---
 
 ## 1. 核心痛点与交付哲学
 
 ### 1.1 核心痛点分析
 1. **过程掩盖结果**：过去 Agent 仅专注于在 `flow/plan.md` 中做任务状态流转，任务完成后直接剪切至 `flow/history/` 归档。一旦归档，项目到底交付了哪些实体资产（代码、脚本、API、文档、镜像）在活跃区彻底消失，人类管理者无法全景掌握交付进度；
 2. **交付物真理源缺失**：缺乏一个全局、集中、随项目演进持续累积的**“交付物法定总账（Deliverables Ledger）”**；
 3. **验收凭证与可运行入口脱节**：许多任务声称“已交付”，但缺乏一行可执行的 Exit 0 自验命令，缺乏本地或云端的预览与运行入口。
 
 ### 1.2 交付哲学（Delivery-First）
 - **任务是过程，交付物才是资产**：Task 终将归档，但 Deliverable 永续存在；
 - **无实体不交付**：严禁口头承诺或文档伪装代码，每一个交付项必须指向真实磁盘物理路径；
 - **无自验证明不移交**：每一个交付物必须具备一行确定性验证命令与 Exit 0 运行证据。
 
 ---
 
 ## 2. 交付物四级生命周期 (Deliverable Status Lifecycle)
 
 每个交付物在 `flow/deliverables.md` 中严格遵循以下四级状态流转：
 
 | 状态代码 | 状态名称 | 定义与准入标准 |
 |:---|:---|:---|
 | **`Draft`** | **设计草案** | 规格、接口契约或架构设计阶段，已明确物理落地路径与预期产物，但代码尚未落盘。 |
 | **`WIP`** | **开发中 (Work in Progress)** | 正在本地编码实现，模块骨架已建立，部分代码已落盘，正处于迭代中。 |
 | **`Landed`** | **代码落盘自验 (Landed & Verified)** | **核心代码 100% 落盘**，通过本地构建与自动化测试（Exit 0 凭证，耗时 < 3s），具备本地运行或预览入口。 |
 | **`Accepted`**| **生产验收可交付 (Production Ready)** | 经人类用户验收通过，满足上线或并网条件，已完成部署或归档发版。 |
 
 ---
 
 ## 3. 交付契约三要素 (Delivery Contract Triad)
 
 任何向项目交付的实体资产，必须在登记时锁定三要素：
 
 ```text
 ┌────────────────────────────────────────────────────────────────────────┐
 │                     【交付契约法定三要素】                             │
 ├────────────────────────────────────────────────────────────────────────┤
 │ 1. 物理实体路径 (Physical Path)   : 必须为仓库内真实存在的绝对/相对路径 │
 │ 2. 确定性验证命令 (Verify Command): 单行可复现的自测命令 (Exit 0 保证)  │
 │ 3. 可运行/预览入口 (Live Entrance): 本地端口、URL、可执行脚本或原型入口 │
 └────────────────────────────────────────────────────────────────────────┘
 ```
 
 ---
 
 ## 4. 任务与交付物双向强联锁门禁 (Task-Delivery Lock Gate)
 
 为防止“任务流转与交付物脱节”，设立两大强制联锁门禁：
 
 ### 门禁 A：提请验收联锁 (Pending Lock)
 - **规则**：`flow/plan.md` 中的任何功能性任务，在由 `[ ] 待完成` 变更为 `[-] 待验收` 时：
   - **必须**在 `flow/deliverables.md`（内部总账）和 `docs/DELIVERY_PREVIEW.md`（外部大盘）中**同步新增或更新对应交付物条目**；
   - 将交付物状态置为 `Landed`，并如实填报验证命令与入口；
   - 若未登记交付物，严禁将任务置为 `[-]`！
 
 ### 门禁 B：完工归档联锁 (Archive Lock)
 - **规则**：当人类用户确认验收通过，任务由 `[-]` 转为 `[✓] 已完成` 并被物理剪切移入 `flow/history/` 时：
   - **任务条目移入历史归档，但交付物条目必须永久保留在 `flow/deliverables.md` 中**！
   - 将该交付物的状态由 `Landed` 正式晋级为 `Accepted`；
   - 确保 `flow/deliverables.md` 永远记录着项目从诞生至今所交付的全部有效资产。
 
 ---
 
 ## 5. 交付物双表物理架构
 
 项目维护两份互补的交付物清单，分别服务 Agent 内部状态与人类全景审查：
 
 ### 5.1 内部总账：`flow/deliverables.md`
 - **作用**：Agent 全局控制面的核心资产总账（与 `plan.md`、`decisions.md` 同级）；
 - **特点**：结构化、包含完整元数据、不可随意清空、持续累加、支持自动化解析。
 
 ### 5.2 外部大盘：`docs/DELIVERY_PREVIEW.md`
 - **作用**：面向人类管理者、技术评审与各端协同人员的“交付全景看板”；
 - **特点**：图表化、高可读性、直观罗列每个模块的交付进度、一键验证命令集合与各端访问入口。

 ## 6. 标准交付物模板与规范样例
 
 ```markdown
 ### 交付物条目规范
 - **交付项 ID**: `DELIV-BACKEND-01`
 - **交付名称**: RuoYi-Vue-Plus 5.x SaaS 多租户脚手架与本地依赖编排
 - **所属阶段**: Milestone 1 (核心微服务与数据底座)
 - **物理资产路径**: `src/zhengjie-backend/`, `src/docker/docker-compose.yml`
 - **交付状态**: `Landed` (已落盘待验收)
 - **确定性验证命令**: `docker compose -f src/docker/docker-compose.yml ps && mvn -f src/zhengjie-backend/pom.xml test`
 - **访问与预览入口**: 后端 Swagger UI: `http://localhost:8080/doc.html`
 - **质量凭据**: 本地 Exit 0，单元测试 100% 转绿，OpenCodeReview 0 严重告警
 ```

 ## 7. 违背惩处
 
 凡出现以下行为，一律判定为交付事故并在 `flow/plan.md` 中打标 `[✕] 不合格` 强制重构：
 1. 在对话或任务看板中声称“已完成”，但 `flow/deliverables.md` 查无此物；
 2. 交付物路径指向空目录、虚构路径或已废弃的旧临时文件；
 3. 填报的验证命令执行失败（Exit code != 0）或存在未捕获的严重阻塞异常。
 
 本 SOP 自发布之日起严格执行，纳入所有 Agent 的 DoD（完成标准）硬门禁。
