# <项目名> · 协作约定(Claude Code / Codex 共用入口)

> `CLAUDE.md` 软链到本文件,两个工具读同一份。**真相源在文件里,不在对话里。**
> 本文件是**运行时合同**:精要规则 + 约束 + 指针。完整详规在 `flow/规范/`。

## 目录地图(哪个文件夹放什么)
- 根级 `flow/` — 唯一控制层(项目"怎么跑"):`charter.md` 目标 / `plan.md` 活跃计划=当前契约 / `进展.md` 进展日志(顶部=最新交接棒)/ `decisions.md` 决策日志 / `踩坑记录.md` 问题与经验库 / `tasks/` 任务卡 / `archive/` 历史已完成任务与计划回收区 / `规范/` 方法论详规
- 根级 `docs/` — 集中内容层(项目"做出什么"):产品 / 架构 / `contracts/` 跨模块契约 / `modules/` 模块说明 / 评审和产出说明
- `<子项目>/`、`scripts/` 或 `src/` — 代码、测试、构建与运行配置;有独立职责的子项目用局部 `AGENTS.md` + `CLAUDE.md` 记录本模块规则
- `DESIGN.md` — (可选)设计 / 创意决策
- **判据**:协调 / 推进总体项目的 → 根级 `flow/`;需要统一发现的知识和方案 → 根级 `docs/`;代码 → 对应子项目。默认不在子项目重复建 `flow/` 或 `docs/`

## 多子项目边界
- 前端、后端、落地页等共享同一仓库和总体目标时,共用根级 `flow/`、`docs/` 和 hook。
- 每个有独立职责的子项目只建局部规则入口,不复制总体计划、交接或文档体系。
- 已有 README、生成文档或必须紧贴代码维护的说明可以留在模块内,但要从根级 `docs/README.md` 建索引。
- 子目录有独立 `.git`、版本、发布或团队边界时,按独立项目处理;完整判断见 `flow/规范/多子项目结构.md`。

## ⚡ 核心铁律: 用户即时指令最高优先级 (Prompt Priority)
1. **当前会话指令高于历史文档**: 用户在当前会话明确给出的指令（如具体修改、范围约束、"不要历史需求"、"只看当前N条"、"停止某任务"）是最高指令源，即时覆盖 `flow/plan.md` 与历史任务。严禁被历史任务绑架或忽视用户当面指令。
2. **"真相源在文件里"的准确定位**: 系统的架构、配置、契约与代码产出必须落盘到实体文件（不只留在口头），**绝不是指用历史文件中的旧计划去推翻或忽视用户当前的即时指令**。
3. **快速通道响应**: 针对用户的单点 Bugfix、UI 微调、配置修改或紧急排查，直接在代码/配置中解决并快速验证，严禁强制铺开全量重型评审文档流程。

## 🛡️ 核心机制: 任务生命周期与物理回收 (Zero-Lingering Task GC)
1. **完成即物理移出 (Cut on Done)**: 任务一旦完成，**立即从 `flow/plan.md` 中物理剪切移入 `flow/archive/`**。`flow/plan.md` 中严禁留存任何已完成的 `[x]` 项，物理消除历史上下文污染！
2. **活跃区纯净原则**: `flow/plan.md` 仅维护当前正在推进的 1~2 个未完成任务（`[ ]`）。无活跃任务时置为 `IDLE`。
3. **任务卡与日志净化**: `flow/tasks/` 完成卡片即刻移入 `flow/tasks/archive/`；`flow/进展.md` 超 15 条即滚动归档至 `flow/archive/`。

## 开工前必读
1. **用户当前指令**: 仔细审读用户本回合的具体要求与约束（最高优先级）
2. `flow/charter.md` — 目标 / 范围 / 约束 / 成功标准
3. `flow/plan.md` — 当前活跃计划(**契约**,未确认不要偏离活跃任务,已完成项忽略)
4. `flow/进展.md` **顶部一条** — 上一棒最新交接棒(做了啥 / 产出路径 / 下一步)
5. 你被分配的任务卡:`flow/tasks/<...>.md` (若有)
6. 当前目录若有局部 `AGENTS.md`,同时遵守其中的职责边界和模块约束

## 收工前必做
1. 在 `flow/进展.md` **最上面追加一条进展**(做了什么 / 为什么 / 怎么理解 / 产出路径 / 问题→解决 / 下一步),**并把这条同时贴在回复里**(让用户当场看到、能直接复制给别的 Agent)——这条就是交接棒。
2. 阶段或任务完结时: 及时将已完成任务移入 `flow/archive/`，保持 `flow/plan.md` 活跃区干净精简。
3. 决策追加 `flow/decisions.md`;问题 / 踩坑追加 `flow/踩坑记录.md`。
4. 文档自检:本轮若动了结构 / 方向 / 约定,主动提议更新本文件(见「文档维护」)。

## 核心约束(铁律)
- 用户当面指令第一，严禁僵尸任务复读。
- 审稿模型 ≠ 产出模型(重大交付前换另一个模型评审)。
- 产出落文件,不留在对话里;单次执行产出相对路径清晰。
- 先 plan 后 act,计划即契约;要改先改 `flow/plan.md`。
- 一会话一焦点。
- 单仓只保留一套总体控制层;模块任务通过任务卡和产出路径区分。
- 产物本身是真相唯一来源;文档只补"看产物看不出的为什么"。
- 解决问题从根本上解,不打补丁。
- 进展条 / 交接只带「指针 + 增量」,不重抄内容。

## 文档维护(精要)
出现新的设计哲学 / 心智模型 / 方向、结构或契约调整、长期约定、需持续参考的外部资料 → 主动**提议**修改点等确认,不擅自写。只沉淀"看产物看不出的为什么";就近写;保持精简。
完整规范:`flow/规范/文档维护SOP.md`;设计 / 创意类归 `DESIGN.md`(`flow/规范/DESIGN维护SOP.md`)。
