# 任务四状态机与按需加载 SOP (Task State Machine & On-Demand Loading SOP)

> 解决 Agent 历史包袱过重、旧任务反复执行、乱入需求干扰与验收不闭环的根本方法论。

---

## 1. 任务四状态机定义 (The 4 Task States)

```
        ┌─────────────────────────────────────────────────────┐
        │                 [ ] 待完成 (TODO)                    │
        │  用户本次下达(最高P0) / 待办排队(按需激活)            │
        └──────────────────────────┬──────────────────────────┘
                                   │ Agent 执行交付
                                   ▼
        ┌─────────────────────────────────────────────────────┐
        │                [-] 待验收 (Pending)                  │
        │  已交付，等待用户确认。Agent 绝对静默，不要去管！   │
        └──────────────┬───────────────────────▲──────────────┘
                       │                       │
         用户验收通过   │                       │ 用户判定不合格，指出缺陷
                       ▼                       │
        ┌──────────────────────────┐   ┌───────┴──────────────┐
        │      [✓] 已完成 (Done)    │   │    [✕] 不合格 (Fix)   │
        │  彻底完结，物理移入归档区  │   │  最高优先级P0，立即修改 │
        └──────────────────────────┘   └──────────────────────┘
```

### (a) `[ ]` 待完成 (TODO)
- **定义**: 尚未开始或正在进行中的任务。
- **调度规则**:
  - **当前会话任务 (Focus Task)**: 用户在当前对话中下达的任务，**优先级最高 (P0)**，必须立即执行！
  - **排队任务 (Backlog Task)**: 后续规划任务，处于待命排队状态，不抢占当前焦点。

### (b) `[-]` 待验收 (Pending Verification)
- **定义**: 上一轮已经执行完毕并交付产物，但**用户尚未明确确认是否合格**的任务。
- **调度规则**:
  - **低优先级 / 绝对静默**：Agent **严禁自发重复执行、严禁重新扫描排查、严禁当成待办任务去处理**！
  - 仅作为状态看板展示，静默等待用户验收反馈。

### (c) `[✓]` 已完成 (Done)
- **定义**: 用户在验收过程中明确确认合格、彻底完结的任务。
- **调度规则**:
  - **物理剪切归档 (Instant Task GC)**: 验收通过后，**立即从 `flow/plan.md` 活跃区物理剪切移入 `flow/history/`**，活跃文件物理禁止留存已完成文本，消除上下文污染。

## 5. Gemini 零缓存中转硬熔断与平滑接力规范 (Gemini Zero-Cache Relay Gate)

### 5.1 为什么必须对 Gemini 施加物理级硬熔断？
在 Codex 接入第三方中转路由（如 AiMaMi → WOYAO.PRO）场景下，实测 Gemini 系列模型（如 `gemini-3.8-flash-high`）在 OpenAI 兼容协议下上下文缓存命中率恒为 **0%**。这意味着：
- 每次交互，历史所有 Token 均被全额重复计费；
- 当会话到达 50~100 轮、上下文膨胀到 40~50 万 Tokens 时，单次简单的读取/修改指令将消耗数百至数千倍费用；
- 单日单个 400+ 轮的长会话会消耗数亿 Token，直接引发十倍账单暴增。

### 5.2 物理级硬限阈值
只要当前使用的模型包含 `gemini`：
1. **轮次阈值**: 单会话交互轮次 **严格 ≤ 25 轮**（20 轮进入预警区，25 轮硬熔断）；
2. **上下文阈值**: 单会话累计输入 Tokens **严格 < 10 万 Tokens**；
3. **工具调用阈值**: 单任务工具调用次数 **严格禁止超过 100 次**。

### 5.3 超限处置与强制接力标准动作
当检测到达到上述任一阈值时，Agent 必须执行以下标准动作，**严禁在当前会话中继续硬扛**：
1. **立即中止继续写码**: 停止当前正在执行的大型业务代码改动，收拢当前断点；
2. **断点物理落盘**: 将当前已写好的代码/测试落盘，并在 `flow/进展.md` 顶部追加最新接力棒（交代已完成项、剩余未完成项的 SDD 原子清单及写入白名单）；
3. **输出标准化接力提示词卡**: 在当前回复最显眼位置输出【会话超限熔断与接力提示词卡】，提示用户直接复制并在新会话中黏贴触发。

#### 标准接力提示词模板 (可直接复制):
```markdown
继续执行任务，请读取 `flow/plan.md` 与 `flow/进展.md` 顶部的最新接力棒。
当前任务为上一会话熔断交接，请以当前磁盘真实代码与进展为真理源，严格在以下白名单范围内继续推进下一个未完成项：
- 目标任务: <P0-x 任务简述>
- 写入白名单: <指定文件绝对路径>
请先在首行正面汇报接力状态，再开始执行。
```
### (d) `[✕]` 不合格 (Rejected / Needs Revision)
- **定义**: 用户在验收过程中指出问题、判定不合格的任务。
- **调度规则**:
  - **最高优先级 (P0)**：Agent 收到反馈后，**必须在当前会话中立即定位原因并进行修改重构**，修复完成后再次转为 `[-] 待验收`。

## 2. 任务按需加载机制 (On-Demand Loading)

### 2.1 为什么必须按需加载？
全量加载历史任务是导致 Agent “注意力涣散、死循环、被乱入需求带偏”的根本原因。
模型上下文必须保持极高信噪比。

### 2.2 按需加载三大准则
1. **焦点最小化**: 开工时，仅装载与当前任务直接相关的输入、契约与代码路径；

### 2.3 进展日志分页与交接棒格式（硬约束）

`flow/进展.md` 是唯一会被下一次开工读取的历史文件，必须分页，否则历史会挤占上下文预算：

- **分页由 `flow-gc.py` 自动执行**：条数超过 5 条、或文件超过 12KB 即滚动；
- **归档去向** `flow/history/progress/进展_YYYYMM.md`，按月分卷，可回溯；
- **标题必须用 `## `**（`### ` 也兼容识别），否则旧版本不会触发滚动；
- **单条交接棒 ≤ 1200 字节**，超出说明在复述背景而非交接状态。

交接棒固定四字段，缺一即视为未交接：

```markdown
## YYYY-MM-DD · <任务> · <谁>
- 现状: <已做到哪，具体到文件路径或已通过的 Exit 0 命令>
- 还剩: <未完成项清单>
- 卡在哪: <熔断原因 / 缺什么 / 无>
- 下一步: <接手方第一条具体命令>
```

**为什么**：旧实现只按条数分页且只认 `## `，实测 o2o 的进度文件涨到 86KB / 41 条仍未滚动，
每次开工把这 86KB 全量灌进上下文，会话必然在 100 次工具调用前耗尽预算而熔断——
表现为“同一任务拆了三四个会话还没做完”。
2. **历史隔离化**: `flow/history/` 历史归档文件默认**绝不主动加载**；
3. **状态过滤化**: 读取 `flow/plan.md` 时：
   - 聚焦处理 `[ ]` (当前任务) 与 `[✕]` (不合格重修任务)；
   - 过滤忽略 `[-]` (待验收任务) 与已归档内容。

## 3. 闭环验收操作流 (Acceptance Loop)

1. **执行交付**: Agent 修改代码/产物并验证后，将该任务在 `plan.md` 中标记为 `[-] <任务描述> (已交付待验收)`；
2. **用户验收**:
   - 若用户确认 OK -> Agent 将该项标记为 `[✓]` 并**立即剪切移入 `flow/history/`**；
   - 若用户指出不合格 -> Agent 将该项标记为 `[✕]`，并作为本轮最高优先级任务立即修改。

## 4. 任务与进展分级垃圾回收机制 (Rolling History & Explicit Trash)

为彻底解决上下文膨胀、保持活跃看板极致信噪比，建立两级物理隔离机制：

```
                    ┌────────────────────────────────────────┐
                    │       活跃控制区 (Active Pool)         │
                    │ plan.md (≤2项) / 进展.md (最新3~5条)   │
                    └───────────┬────────────────┬───────────┘
                                │                │
                   正常验收通过 │                │ 判定废弃/推翻重做
                   滚动超出限制 │                │ 方向错误作废
                                ▼                ▼
            ┌────────────────────────┐  ┌────────────────────────┐
            │   flow/history/ 归档区  │  │    flow/trash/ 废弃区   │
            │ (供日后追溯，开工不加载)│  │ (彻底隔离，绝不复读)    │
            └────────────────────────┘  └────────────────────────┘
```

### 4.1 历史任务与日志滚动归档 (`flow/history/`)
1. **活跃日志只留最近 3~5 条**：`flow/进展.md` 仅保留最近 3~5 次交接棒。超过 5 条时，自动将下方旧记录剪切沉淀至 `flow/history/progress/进展_YYYYMM.md`；
2. **任务卡完结归档**：任务一旦标记 `[✓]`，其实体卡片 `flow/tasks/Txx.md` 立即剪切移入 `flow/history/tasks/`；
3. **溯源隔离**：`flow/history/` 仅在用户明确要求“查阅历史/追溯变更”时主动索引，日常开工默认**绝不读取**。

### 4.2 废弃任务与垃圾回收 (`flow/trash/`)
1. **定义与触发**：当用户在任务推进中判定“方向不对、废弃此方案、重构此模块”时；
2. **即时物理移出**：Agent 立即将废弃的草稿、无效方案、错误代码或废弃任务卡物理移入 `flow/trash/`，并在记录中打上 `[TRASHED/DEPRECATED]` 标记；
3. **绝对隔离**：`flow/trash/` 中的任何内容严禁再次作为待办或需求被 Agent 读入上下文。

## 5. 双轨决策与人工决策升级门 (Decision Engine & Escalation Gate)

为平衡“自主执行效率”与“系统安全可控”，决策机制分为 **Agent 自动决策** 与 **人工决策升级门**：

### 5.1 Agent 自动决策 (Automated Decisions)
- **适用范围**：
  1. 局部技术实现细节（如：函数与变量命名、内部模块拆分、CSS 样式选择器、正则表达式优化）；
  2. 非破坏性重构与性能调优（在完全满足现有契约与接口定义的前提下）；
  3. 异常捕获与防御性代码编写。
- **执行准则**：
  - Agent 自主裁决并落地执行，无需暂停打断用户；
  - 执行完毕后，将关键技术选择与原因以简明条目自动追加至 `flow/decisions.md`（指针式记录）。

### 5.2 人工决策升级门 (Human Escalation Gate)
- **核心铁律：自动决策是默认常态，人工决策仅作为第二重安全门！**
- **严禁滥用人工决策打断用户**：日常代码实现、函数封装、CSS 样式选择、常规重构等常规动作**一律由 Agent 自动决策并记录**。
- **触发人工决策的严格条件（必须暂停并输出人工决策卡）**：
  1. **极高风险/破坏性改动 (High Risk)**：
     - 删除或覆盖未备份的关键业务数据、数据库表结构或重要历史日志；
     - 涉及线上支付、资金结算、身份鉴权与权限越权等安全核心逻辑；
     - 废弃生产环境正在使用的公共 API 接口契约或大范围破坏既有对外协议。
  2. **用户明确强制要求 (Explicit User Mandate)**：
     - 用户在 Prompt 中明确指明：“让我确认后再改”、“列出方案让我选”、“此处需要我人工决策”等；
     - 需求存在重大歧义且不同选型方案的成本/风险差异极大，盲目猜测会导致严重返工。
  3. **架构颠覆与主线废弃**：
     - 引入新的重型依赖/全套框架、推翻项目根级目录结构；
     - 涉及将已交付的主干功能判定推翻废弃并物理移入 `flow/trash/`。
- **交互协议 (Decision Card Protocol)**：
  一旦命中上述条件，Agent **严禁擅作主张盲目修改**，必须在回复中输出【人工决策卡】：
  ```markdown
  ⚠️ 【人工决策升级门】检测到关键架构/业务选型分歧，请用户确认：
  - 决策议题: ...
  - 选项 A: ... (优势: ..., 风险/代价: ...)
  - 选项 B (推荐): ... (优势: ..., 风险/代价: ...)
  - 建议方案与原因: ...
  - 请回复确认选择（A / B 或其他指令），确认后方可继续执行。
  ```
  输出后进入静默等待，直至用户给出明确选择。

## 6. 看板视觉降噪与智能标签规范 (Clean Badge & Visual Protocol)

### 6.0 开工状态与收工看板必须分离

- 开工只输出：当前聚焦 `[ ]`、路由阻塞、未纳管遗留和预算；
- 开工不得预填 `[-] 待人工验收`、`[✓] 已归档` 或“本轮决策”；
- 收工阶段只有在任务完成、验证留有 Exit 0 证据后，才输出完整四状态看板、本轮工作汇报和交付验收卡；
- `flow-boot.py` 的开工输出使用“项目开工状态”，`flow-deliver.py` 的收工输出使用“交付验收卡”。

收工工作汇报必须包含原始六字段，任务看板不能代替它：

```text
做了什么
为什么这么做
怎么理解
产出路径
问题 → 怎么解决
下一步
```

### 6.1 独立代码块 To-Do 清单铁律
- **严禁使用 ASCII 边框画框**（如 `╔═══╗`、`║` 等）：由于中英文字符宽度不一致，在终端与 Markdown 渲染器中会导致严重的左右对齐错乱与排版灾难；
- **强制使用独立代码块 (Code-Block) 包裹的 To-Do 清单**：
  将状态名称作为独立二级标题 (`## 🎯 当前聚焦待办 (P0)` 等)，下方换行后统一使用 Markdown `- [ ]` / `- [-]` / `- [✓]` 规范列表，视觉独立、边界清晰、绝对不会挤在同一行。

### 6.2 验收类型与决策标签
在看板与验收卡中必须显式打上类型标签：
1. **验收分类标签**：
   - `[🤖 自动验收通过]`：已通过 E2E/单元测试/接口断言自动化跑通，附带自动化测试证据；
   - `[👤 待人工验收]`：涉及界面交互、体验感官或业务逻辑，需要用户最终确认。
2. **决策类型标签**：
   - `[⚡ 自动决策]`：Agent 在内部实现细节、性能调优、重构中的自主裁决（已记录在 `decisions.md`）；
   - `[⚠️ 人工决策门]`：遇到高风险/破坏性改动/方案分歧，暂停并提请用户选择。

## 7. 规划分域隔离与原路归流排队机制 (Domain Queueing & Return-to-Origin Routing)

### 7.1 为什么规划会出现“乱入”？
- **根因一：跨项目会话串音**: 在一个工作区（如电商）会话中提问另一个工作区（如小说生成器）的问题，Agent 误将外域内容写进当前项目的 `flow/plan.md` 或 `flow/进展.md`；
- **根因二：多子模块规划未分域**: 多个子端（C 端、B 端、运营端）的任务全部扁平塞入根级 `flow/plan.md`，导致任务互相穿插、发散失控。

### 7.2 杜绝乱入的三大防线
1. **项目边界硬隔离 (Project Boundary Guard)**:
   - Agent 收到指令时，首先核验其所属项目。若是临时问答或非本仓库代码，**严禁将其作为待办写入当前项目的 `flow/plan.md` 或 `flow/进展.md`**，仅就题答题。
2. **任务分发到原处 (Dispatch to Origin)**:
   - 复杂项目的多个子规划，必须在 `flow/tasks/<模块>/`（如 `flow/tasks/c-app/`、`flow/tasks/b-web/`）建立专属任务卡排队，避免多端任务混为一谈。
3. **完成原路归流与归档 (Return-to-Origin GC)**:
   - 当某个子端任务完成后，状态必须**原路回写至该模块的任务卡与所属子规划中**；
   - 验收通过后，归档至 `flow/history/tasks/<模块>/`；
   - 根级主看板 `flow/plan.md` 永远只保留当前激活的 1 个 P0 焦点，其余待办全部在原模块有序排队，杜绝主控面爆炸。
