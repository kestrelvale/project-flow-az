# Sub-Agent 多 Agent 并行协作与派发 SOP

> **适用场景**：复杂功能开发、多端跨模块重构（如前端+后端+文档）、重型长图/大文件解析、以及需要独立上下文深度排障的场景。  
> **核心目标**：通过 Codex 的 `spawn_agent` / `wait_agent` 机制，将单一臃肿会话解耦为“主控架构师 + 专业执行子 Agent”，彻底根治单 Agent 上下文爆炸、认知过载与半路偷懒交卷问题。

---

## 1. 角色分工模型 (Role Architecture)

```
┌──────────────────────────────────────────────────────────────┐
│                 主控 Agent (Orchestrator)                     │
│  - 唯一维护全局 flow/ 控制面 (plan.md / 进展.md / decisions)   │
│  - 任务切片分解 (Disjoint Write Sets) 与子 Agent 派发         │
│  - 结果物理校验 (Diff / Build / Test) 与合并归档 (Task GC)     │
└───────────────┬──────────────────────────────┬───────────────┘
                │ spawn_agent                  │ spawn_agent
                ▼                              ▼
┌──────────────────────────────┐┌──────────────────────────────┐
│   Worker Agent A (前端/H5)   ││   Worker Agent B (后端 API)   │
│ - 独立轻量上下文             ││ - 独立轻量上下文             │
│ - 专注前端代码修改与自测     ││ - 专注后端 Controller/Service│
│ - 交付文件列表与变更摘要     ││ - 交付接口与单元测试         │
└──────────────────────────────┘└──────────────────────────────┘
```

### 1.1 主控 Agent (Orchestrator) 铁律
1. **控制面唯一所有者**：只有主控 Agent 拥有读写 `flow/plan.md`、`flow/进展.md`、`flow/decisions.md` 的权限。**子 Agent 绝对严禁直接修改 `flow/` 控制文件**，防止写冲突与状态撕裂。
2. **无交叠写入边界 (Disjoint Write Sets)**：派发前必须规划好每个子 Agent 的文件修改范围，严禁两个子 Agent 同时修改同一个代码文件。
3. **本地物理集成与验收**：子 Agent 完成后，主控 Agent 必须在本地工作区检查修改文件、执行构建与测试，自检通过后统一在 `flow/进展.md` 追加进展日志。

### 1.2 执行子 Agent (Worker Sub-Agents) 职责
1. **单点聚焦，拒绝臃肿**：子 Agent 在干净或专有上下文中运行，不加载主会话的历史多轮聊天；
2. **代码落盘自测**：在自己的隔离环境中直接完成文件修改，并输出改动文件清单（`files_modified`）与测试结果；
3. **不自作主张**：遇到跨边界改动或破坏性变更时向主控 Agent 报告，不擅自越界。

## 2. 任务派发与协同标准流程 (SOP)

### 步骤一：任务切片与边界定义 (Task Decomposition)
主控 Agent 接收到复杂需求时，先分析依赖树，切分为 1~3 个无交叠子任务：
- **切片 A (前端端)**: 页面组件、样式、交互事件（如 `src/views/`、`pages/`）；
- **切片 B (后端端)**: 数据库迁移、Entity、Mapper、Service、Controller（如 `yudao-module-*/`）；
- **切片 C (专项测试/文档)**: E2E 测试用例、接口契约文档、使用手册（如 `docs/`、`tests/`）。

### 步骤二：调用 `spawn_agent` 派发子 Agent
派发 Prompt 必须具备**极高精度与约束**：
```markdown
你是一个专业的 [前端/后端/测试] 执行 Worker。
【目标】：完成 <具体功能点> 的代码编写与自测试。
【写入边界】：你只能修改以下文件：
- path/to/fileA.vue
- path/to/fileB.ts
【约束】：
1. 严禁修改 flow/ 目录下的任何文件；
2. 修改完成后执行本地单点测试验证；
3. 最终回复仅输出：[修改的文件列表] + [核心改动说明] + [测试结果]。
```

### 步骤三：并行等待与非阻塞集成 (`wait_agent`)
1. 派发后主控 Agent 可本地执行无交叠的准备工作或直接 `wait_agent` 等待子 Agent 完成；
2. 子 Agent 状态到达 `completed` 后，主控 Agent 提取其产出的文件列表并执行 `git diff` 审阅。

### 步骤四：收工自检与四状态看板流转
1. 主控 Agent 运行整体构建与全量自测（`mvn compile` / `npm run build` / 单测）；
2. 验证全部通过后，在第一屏输出【任务四状态机看板】，将任务置为 `[-] 待验收`；
3. 在 `flow/进展.md` 顶部追加交接记录，完成一轮完整闭环。

## 3. 防半路交卷与防并发冲突四大硬门禁

| 门禁序号 | 门禁名称 | 强制规则 | 违规后果 |
|:---|:---|:---|:---|
| **Gate 1** | **代码落地硬门禁** | 功能/修复类需求，必须有实体代码修改与构建测试，**严禁仅写分析文档交差**。 | 判定为不合格，强制打回继续编码。 |
| **Gate 2** | **Disjoint Write Set 门禁** | 派发多个子 Agent 时，写入文件列表交集必须为空（WriteSet_A ∩ WriteSet_B = ∅）。 | 禁止派发，必须先重构切片范围。 |
| **Gate 3** | **控制面单写门禁** | 严禁子 Agent 读写 `flow/` 控制面文件。 | 污染主看板，导致状态机混乱。 |
| **Gate 4** | **自检反查门禁** | 收到 `【收工自检】` 拦截时，强制反查子 Agent 是否全量完工且代码已落盘。若否，立即继续执行。 | 杜绝假完工与半路交卷。 |
